### <img src="https://raw.githubusercontent.com/primer/octicons/main/icons/comment-discussion-16.svg" width="20" height="20" /> Mission Reflection

Establishing proactive system baseline monitoring prior to deploying containerized applications into production is a critical foundational practice in Site Reliability Engineering. By rigorously evaluating available host resources—including RAM allocation via `free -h`, disk storage capacity via `df -h`, and process execution via `top`—cloud operations engineers ensure that underlying host infrastructure possesses sufficient headroom to absorb unexpected traffic surges. Without these baseline measurements, teams risk deploying services onto underprovisioned environments, leading directly to catastrophic resource starvation, severe disk I/O bottlenecks, and unexpected service disruptions. Furthermore, during active incident response and debugging, real-time container metrics (`docker stats`) and application logs (`docker logs`) serve as complementary diagnostic pillars. High-level telemetry provided by container metrics quickly highlights macro-level anomalies such as minimal CPU usage or precise memory footprints (e.g., 2.74MiB), alerting engineers to operational stress points across containerized workloads like our Nginx `client-website` container. Meanwhile, granular application access and error logs delve into the micro-level root causes, recording precise chronological timestamps, client IP addresses, requested URIs, and exact HTTP status codes—such as successful `200 OK` responses alongside `404 Not Found` errors generated by simulated `curl` requests to hidden administrative endpoints. By combining quantitative metric tracking with qualitative log inspection, cloud engineers eliminate guesswork, enabling rapid root cause isolation, streamlined incident mitigation, and the sustained reliability of modern cloud-native architectures.
